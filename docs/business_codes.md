# mini-mall 业务错误码约定

接口测试的核心不是“通不通”，而是“失败时是否符合约定”。本表同时作为 AI 生成用例的输入上下文。

## 信封格式

```json
{ "code": 0, "message": "ok", "data": {} }
```

- `code == 0` 表示业务成功；
- `code != 0` 表示业务失败，`message` 为可直接展示给用户的原因；
- HTTP 状态码只表达传输/鉴权/权限/限流语义，**业务失败默认仍是 HTTP 200**。

## 错误码

| code | HTTP | 含义 | 典型触发 |
| --- | --- | --- | --- |
| 0 | 200 | 成功 | — |
| 1001 | 200 | 用户名或密码错误 | 密码错误、用户不存在 |
| 1002 | 200 | 商品已下架 | 对 `onSale=false` 商品下单/加购 |
| 1100 | 400 | page 非法 | `page=0` |
| 1101 | 400 | size 超范围 | `size=51` |
| 2002 | 200 | 库存不足 | 数量大于 `stock` |
| 3001 | 409 | 订单状态不允许支付 | 重复支付、支付已取消订单 |
| 3002 | 409 | 订单状态不允许取消 | 取消已支付订单 |
| 4001 | 401 | 未登录/缺少 token | 无 `Authorization` 头 |
| 4002 | 401 | token 无效或过期 | 伪造签名、过期 |
| 4003 | 403 | 无权限 | 越权查看/操作他人订单、普通用户访问管理端 |
| 4004 | 404 | 商品不存在 | `/api/products/999` |
| 4005 | 404 | 订单不存在 | `/api/orders/99999` |
| 4009 | 403 | 测试模式未开启 | 调用 `/api/_test/reset` |
| 4029 | 429 | 登录失败次数过多 | 同一账号 60 秒内失败 5 次 |
| — | 422 | 参数结构与类型校验失败 | 缺字段、`quantity=0`、类型错误（由 FastAPI 返回 `detail`） |

## 对测试的要求

1. 每个非 0 错误码至少有一条用例，且同时断言 HTTP 状态码与 `code`；
2. 不允许只断言 `status_code == 200`；
3. 401 与 403 必须区分：未登录是 401，登录了但没权限是 403；
4. 422 由框架抛出，响应体是 `{"detail": [...]}`，不能套用上面的信封断言。
